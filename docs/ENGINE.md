# 모아 계산 엔진 (`src/core`)

기준 문서: **모아 기획서 — 20대의 필수결제 자금 부족을 미리 알려주는 AI (2026-10-29)**.
화면·서버는 `src/core/index.ts`에서만 가져다 쓴다. 숫자(잔고·날짜·부족 금액)는 모두 여기서 계산하고, LLM은 문장만 만든다.

## 엔진이 정한 가정 (발표·신청서에서 그대로 설명할 것)

- **시각**: 고정 출금·카드 대금은 그날 00:00(KST)에 빠진다고 본다. 잔액 확인 시각 t₀가 그날 00:00 이후면 이미 B₀에 반영된 것으로 본다.
- **입금**은 그날 23:59에 들어온다고 본다(같은 날엔 출금 먼저 — 보수적). 잔액 확인한 날과 같은 날 예정인 입금은 `flags.sameDayIncomes`로 "이미 들어왔나요?"를 한 번 묻는다.
- **예정일이 지났는데 안 들어온 입금**은 계산에서 빼고 `flags.overdueIncomes`로 표시한다.
- **등록 일정 기준 부족**은 확정 거래 + 고정 출금 + *예정* 입금으로 계산한다(불확실 입금 제외). 예정 입금이 늦어지는 경우는 '입금 지연' 시나리오가 따로 본다.
- **일정 실현 판단**: 같은 금액의 필수 지출(또는 `scheduleRef`로 연결된 거래)이 예정일 ±3일 안에 있으면 고정 출금이 실현된 것으로 보고 다시 빼지 않는다. 입금은 예정일 −5일~+10일.
- **결제 수단 비중**: 최근 4주 변동 지출이 5건 미만이면 온보딩에서 물은 주 결제 수단, 그것도 없으면 결제계좌에서 바로 빠진다고 본다(보수적). 신용 비중이 있는데 등록된 신용카드가 없어도 결제계좌로 옮긴다.
- **상단 폭 임시값**: 본인 오차 10개 미만이고 공통 오차도 없으면 기본 누적 예측의 50%를 쓴다(`FALLBACK_UPPER_RATIO`). 데이터로 정한 값이 아니다.
- **예측 시점**: 어제까지의 라벨로 오늘부터 예측한다(오늘 라벨은 하루가 끝나야 확정). 새 기록이 들어오면 다시 계산하면 된다 — 엔진은 상태가 없다.
- **결제 판단 기준**: 결제일의 하루 최저 잔고(그날 출금을 다 뺀 직후)가 0보다 작으면 부족.
- **'살까 말까' 가정 거래**는 `planned: true`로 넣어 잔고에는 반영하되 지출 예측·비중·오늘 기록에는 넣지 않는다.

## 합성 사용자 결과 읽는 법

`scripts/synthetic-eval.ts`의 재현율은 높게 나온다. 시뮬레이터와 엔진이 같은 회계 규칙을 쓰고, 부족 대부분이 등록된 일정만으로 보이는 구조적 부족이기 때문이다. **합성 결과는 '탐지 로직이 의도대로 작동하는지'까지만 주장**하고, 실제 사용자 성능이나 사용자 테스트 인원으로 쓰지 않는다.
