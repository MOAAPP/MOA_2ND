# 평행통장 ML 연결 가이드

화면 코드는 ML이 붙든 안 붙든 **같은 모양의 데이터**만 받는다. 지금은 규칙 기반(기준선)으로 돌고,
모델 API 주소를 넣으면 모델 결과로 바뀐다. 모델이 실패하거나 2.5초 안에 답하지 않으면 자동으로 규칙 기반으로 돌아간다.

```
.env
VITE_ML_API_URL=https://<모델 서버>
```

## 구조

| 파일 | 하는 일 | 모델로 바꿀 부분 |
| --- | --- | --- |
| `src/lib/ml/types.ts` | 공통 타입, 기준값(확신 0.6, 부족 확률 20%, 개인화 최소 3건) | – |
| `src/lib/ml/forecast.ts` | 하루 생활비 P10/P50/P90 예측 (규칙 기반) | **LightGBM 분위수 회귀 + conformal 보정** |
| `src/lib/ml/classify.ts` | 상품명 → 카테고리 (키워드 + 내가 고친 기록) | **문자 n-gram TF-IDF + 로지스틱 회귀** |
| `src/lib/ml/montecarlo.ts` | 생활비 경로 3,000개 → 잔고 범위, 부족 확률, 구매 타이밍 | 그대로 사용 (예측 분위수만 바뀜) |
| `src/lib/ml/provider.ts` | 모델 API 호출 + 실패 시 규칙 기반 대체 | 엔드포인트 주소만 |
| `src/lib/ml/csv.ts` | 지출 CSV → 생활비 기록 (최대 5만 줄) | – |
| `src/lib/ml/compute.ts` · `mc.worker.ts` · `engine.ts` | 확률 계산을 Web Worker에서 실행 (화면 안 멈춤), 워커가 없으면 메인 스레드 | – |

## API 계약

### `POST /forecast`

요청
```json
{
  "from": "2026-10-21",
  "to": "2026-11-30",
  "today": "2026-10-20",
  "dailySpend": 13000,
  "history": [{ "date": "2026-10-19", "amount": 4500, "category": "카페", "name": "아메리카노", "from": "record" }]
}
```
- `history`: 오늘 쓴 돈 기록 + 사기 전 확인에서 '샀다/대안' + CSV. 고정지출(월세·통신비·구독)은 빠져 있음.
- `dailySpend`: 온보딩 입력값(없을 수 있음). 신규 사용자 콜드스타트용.

응답 (`SpendingForecast`)
```json
{
  "engine": "model",
  "modelName": "lgbm-quantile-v1",
  "basis": "blend",
  "historyDays": 12,
  "historyCount": 18,
  "personalWeight": 0.4,
  "dummy": true,
  "days": [{ "date": "2026-10-21", "p10": 2000, "p50": 9000, "p90": 24000 }]
}
```
- `days`는 `from`~`to` **하루 단위**, 원 단위 정수.
- `basis`: `none | profile | blend | history`. 기록 3건 미만이면 `profile`(공통 모델 그대로).
- `personalWeight`: 개인화(잔차 보정) 반영 비율 0~1. 화면에 "내 기록 n% 반영"으로 표시됨.
- `dummy`: 더미 데이터로 학습한 모델이면 `true` → 화면에 "더미 데이터 기준" 표시.

### `POST /classify`

요청 `{ "name": "겨울 운동화" }`

응답 (`Classification`)
```json
{ "category": "패션", "confidence": 0.82, "engine": "model", "candidates": [{ "category": "패션", "score": 0.82 }, { "category": "쇼핑", "score": 0.11 }] }
```
- `category`는 `src/lib/categories.ts`의 10개 중 하나.
- `confidence < 0.6`이면 화면이 "골라주세요"로 바뀌고, 사용자가 고른 값은 `categoryMemory`에 저장 → 다음엔 모델보다 먼저 씀.
- 사용자가 고친 분류는 설정 > 생활비 예측 데이터 > **분류 고친 기록 내보내기**로 JSON(`[{name, category}]`)을 받아 재학습에 쓸 수 있음.

## 확률 계산 방식 (montecarlo.ts)

1. 하루 생활비 분위수(P10/P50/P90)를 구간별 선형 보간한 분포로 보고 하루씩 뽑는다.
2. 경로마다 공통 충격(로그정규, σ=0.22)을 곱한다. 날짜끼리 완전히 독립으로 뽑으면 범위가 너무 좁게 나오고 부족 확률이 과소평가되기 때문.
3. 같은 경로 3,000개를 모든 세계(산 나/안 산 나/평행)에 똑같이 써서 세계 간 차이는 선택 차이만 남긴다.
4. 일정·선택으로 만든 결정적 잔고에서 누적 생활비를 빼서 날짜별 P10/P50/P90 잔고, 0원 아래로 내려갈 확률, 지켜둘 금액 아래 확률을 낸다.
5. 구매 타이밍: 후보 날짜마다 "그날 산다"를 1,500개 경로로 돌려 부족 확률이 20% 이하인 가장 이른 날을 추천.

## 발표 때 받을 만한 질문 메모

- **더미 데이터 학습**: 화면에 "더미 데이터 기준"을 띄우고, 규칙 기반 기준선 대비 성능(핀볼 손실, 커버리지)을 같이 보여주면 방어가 쉽다.
- **"브라우저에만 저장"**: 저장은 브라우저에만 하지만 모델 API가 연결되면 예측할 때 기록이 서버로 *전송*된다. 설정 화면 문구에 이미 반영함.
- **기준값 근거**: 확신 0.6 / 부족 확률 20% / 개인화 최소 3건은 `types.ts`에 상수로 모아뒀다. 커버리지 측정 결과로 정했다고 근거를 붙이면 좋다.

## 계산 규모

`tests/scale.test.ts`에서 확인한다.

- 기록 5,000건 + 지출 5,000건 + 경로 3,000개 → 2초 안 (보통 0.1초대)
- 구매 타이밍: 날짜 41개 × 경로 1,500개 → 3초 안
- 지출 CSV 2만 줄 → 1.5초 안
- 경로는 `Float64Array` 한 덩어리에 담고, 타이밍 추천은 날짜별 범위 정렬을 건너뛴다.

## 사진 입력 · 최저가

| 기능 | 서버 키가 있을 때 | 없을 때 |
| --- | --- | --- |
| 가격표·영수증 사진 → 금액 | `POST /api/purchase/ocr` (ANTHROPIC_API_KEY, Claude 비전) | 브라우저 안에서 Tesseract(한국어) OCR — 사진이 기기 밖으로 안 나감 |
| 최저가 | `GET /api/purchase/price?q=` (NAVER_CLIENT_ID/SECRET, 네이버 쇼핑 검색) | 네이버쇼핑·다나와·쿠팡 가격순 검색 링크 |

- 사진은 긴 변 1,400px JPEG로 줄여서 보내고 서버에 저장하지 않는다.
- OCR 결과는 바로 넣지 않고 "이 금액이 맞나요?"로 한 번 확인받는다.
- 최저가는 중앙값의 35%보다 싼 결과(케이스·필름 같은 액세서리)를 빼고 고른다. 찾은 최저가는 '더 싼 걸 산 나'로 바로 비교할 수 있다.
