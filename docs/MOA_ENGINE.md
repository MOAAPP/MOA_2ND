## 규칙 요약

**일별 잔고:** `B̂(t) = B₀ + I − F − D̂ − Ĉ`, t₀ 이후만 누적. t₀ 날짜의 일정·청구는 `anchor.reflected`에 있을 때만 이미 반영된 것으로 봐요.

| 거래 | 결제계좌 반영 |
|---|---|
| 체크카드(결제계좌 연결) · 계좌이체 · ATM | 즉시 |
| 다른 계좌 체크카드 · 지갑 현금 | 반영 안 함 (소비 집계만) |
| 신용카드 일시불 | 이용기간 마감 다음 첫 결제일 |
| 신용카드 할부 | 회차별 결제일 (나머지는 1회차) |
| 카드 대금 출금 문자 | 같은 카드 ±3일 청구 예정을 지우고 실제 금액 사용, 차액은 화면에 안내 |
| 본인 계좌 간 이체 | 결제계좌로 들어오거나 나갈 때만 |
| 적금 납입 | 납입일, 변동 지출 학습에서 제외 |
| 등록 일정과 같은 거래 | `scheduleRef`로 묶어 한 번만 |

**예측:** 기록 2주 미만이거나 정답일 7일 미만이면 예측하지 않고 '등록 일정 기준 부족'만. 이후 요일별 평균. 오늘은 `오늘 예측 − 오늘 이미 기록된 같은 결제 수단 그룹 지출`만 남은 예측으로 넣어요. 신용카드 비중 예측분은 출금일이 계산 범위 밖이면 이번 잔고에 영향 없음.

**상단 폭:** 결제일까지 남은 h일의 '과거 h일 누적 오차' 상위 20%. 창이 5개 미만이면 공통 비율(`COMMON_UPPER_RATIO`, 실데이터로 다시 정할 값). 화면에는 확률 대신 '평소보다 많이 쓰는 경우'.

**등급 제한:** 잔액 7일 넘게 미확인, 또는 최근 7일 안 잔액 불일치가 있으면 '주의'를 넘지 않아요.

## 기획서와 실제 구현이 다른 부분 (기획서 수정 제안)

| 기획서 | 실제 | 제안 |
|---|---|---|
| Supabase insert, RLS, Edge Function 마스킹 | 기록은 브라우저 localStorage에만 저장. 서버(Express/Vercel 함수)는 마스킹된 문자열만 중계하고 저장하지 않음 | "원문과 기록 모두 서버에 저장하지 않는다"로 바꾸면 개인정보 주장이 더 강해져요. RLS·기관 대시보드는 로드맵으로 |
| Vercel Cron 야간 배치 | 앱을 열 때·새 기록이 들어올 때 기기에서 바로 다시 계산 (`MoaAlertsDaemon`) | "새 기록마다 즉시 재계산"으로. 푸시는 브라우저 알림(앱이 열려 있을 때) + 알림함 |
| 예측 행을 실행마다 저장 (`forecast_run_id`) | 예측은 저장하지 않고 매번 계산 (`ForecastResult.runId`만 표시) | 문구만 정리 |
| LightGBM을 서비스에 사용 | 오프라인 Python으로 비교, 채택 조건을 넘을 때만 provider 교체. 현재 앱은 요일별 평균 | 그대로 (기획서 원칙과 같음) |
| 주간 Discord 소비 리포트 | 아직 없음 (기존 Discord는 주식 카드뉴스) | 공용 채널에 개인 소비가 올라가는 문제가 있어 MVP에서 빼는 걸 권해요 |

## 아직 사람이 해야 하는 것

- 팀원 4명 70일 이상 결제 문자 수집 → 앱에서 붙여넣고 '평가용 기록 내보내기' → `data/eval/*.json`
- 은행 앱 거래내역과 대조해 대조 완료일 표시
- `npx tsx scripts/eval/run.ts --real data/eval/*.json` 결과로 신청서 표 채우기
- 외부 대학생 5~8명 시나리오 평가 (교차 설계)
- `ANTHROPIC_API_KEY` 넣고 `VITE_AI_MODE=live`로 LLM 추출기 vs 정규식 파서 50문장 비교
